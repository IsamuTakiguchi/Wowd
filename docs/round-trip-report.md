# ラウンドトリップ差分の記録

`.docx` を開いて無編集で保存したとき、元ファイルと出力に生じる差分のうち
**意図的で問題のないもの**をここに列挙する。

**ここに書かれていない差分はバグとして扱う。**

## 検証手順

```bash
npm run fixtures                      # フィクスチャ生成
npm test                              # 自動ラウンドトリップテスト
npm run verify:roundtrip <file.docx>  # パッケージとXMLの差分を目視確認
```

最終ゲートは実機の Microsoft Word で開き、「問題を修復しますか」が出ないこと。
これは人手でしか確認できない。

## 許容済みの差分

### 1. zip コンテナのバイト列

deflate の実装が異なるため、圧縮後のバイト列は元ファイルと一致しない。
保証しているのは **各パートの中身が 1 バイトも変わらないこと**。
自動テストはパートを展開してから比較している。

タイムスタンプは再現可能性のため 1980-01-02 に固定している。

### 2. `xml:space="preserve"` の有無

Wowd は **空白を含むテキストにだけ** `xml:space="preserve"` を付ける。
一部の生成ライブラリ (テストフィクスチャを作っている `docx` パッケージなど) は
空白を含まないテキストにも無条件で付けるため、そこが差分になる。

`xml:space` は前後の空白の扱いだけを左右する属性なので、
空白を含まないテキストでは付いていても付いていなくても意味は同じ。

### 3. 属性の並び順

`<w:spacing w:after="120" w:before="120"/>` と
`<w:spacing w:before="120" w:after="120"/>` のように、属性の出力順が変わることがある。
XML では属性の順序に意味が無いため問題ない。
(子要素の順序は意味を持つので、そちらは `src/core/docx/write/order.ts` の
順序テーブルで厳密に制御している。)

### 4. `document.xml` の整形

Wowd は要素間に改行やインデントを入れない。
元ファイルが整形されていた場合は差分になるが、WML の意味は変わらない。

### 5. 段落記号の書式 (`w:pPr/w:rPr`) の子要素順

段落記号自体の書式は解釈せず、原文のまま退避して書き戻す。
画面にも保存内容にも効かない飾りなので、モデル化する意味が無いため。

ただし `w:ins` / `w:del` (段落記号そのものの挿入・削除) だけは取り分けて
モデル化する。承諾や取り消しの対象にできる必要があるため。
書き戻すときは `CT_ParaRPr` の規定どおり `w:rPr` の先頭に置く。

### 6. 書き換えるパートの範囲

保存時に書き直すのは次のパートだけで、ほかはバイト列のまま通す。

| パート | 書き直す条件 |
|---|---|
| `word/document.xml` | 常に |
| `word/numbering.xml` | リストやスタイルを編集したとき |
| `word/comments.xml` | コメントを編集したとき |
| `word/commentsExtended.xml` | 同上。無ければパート・リレーション・Content_Types の項目ごと作る |

| `word/header*.xml` / `word/footer*.xml` | ヘッダー / フッターを編集したとき |
| `word/media/*` | 画像を挿入したとき (関係と Content_Types も足す) |

ヘッダー / フッターは、編集していなければ**書き直さない**。
読み込んだ内容がバイト列のまま書き戻される。

## 冪等性テストの盲点と、そこを通った 3 件

**「読み直したモデルが同じになる」(冪等性) だけでは情報の欠落を捕まえられない。**
読み取りが落とし、書き出しも出さない要素は 2 回目もやはり落ちるので、
モデルは一致して素通りする。`scripts/verify-roundtrip.ts` は
`document.xml` の差分を表示はするが、許容済みの差分が常に出るため
判定には使っていない。人が読み飛ばせば、それで終わってしまう。

実際に 3 件がこの穴を通っていた。いずれも Word でしか露見しないか、
**Word でも修復ダイアログが出ず、黙って書式だけが失われる**種類の壊れ方をする。

| 何が | どう壊れていたか | 気づけなかった理由 |
|---|---|---|
| `w:pPrChange` | 変更前の段落書式 (子の `w:pPr`) を読み捨て、属性だけの空要素として書き戻していた。`CT_PPrChange` は子を必須とするので**規格違反**でもある | フィクスチャに `w:pPrChange` が 1 つも無く、スキーマ検証にもかからなかった |
| `textStyle` マーク | モデルは `RunProps` を平らに持つのに、ProseMirror の拡張は `runProps` 1 個の入れ子で宣言していた。**ProseMirror は宣言の無いマーク属性を黙って捨てる**ので、`w:rFonts` (フォント) と `w:sz` (文字サイズ) が「開いて保存しただけ」で消えていた | 単体テストは read → write しか通しておらず、間にエディタが入らなかった。書式を*エディタで付けて*保存する経路は通っていたので e2e も通った |
| `underline` マーク | TipTap 既定の下線は属性を持たない。`w:u` の種類 (二重下線など) と色が同じ理由で消えていた | 同上 |

対策として 2 本のテストを置いた。どちらも全フィクスチャに一斉にかかる。

- `tests/unit/roundTripFidelity.test.ts` — read → write で**要素と文字が減らないこと**
- `tests/unit/editorRoundTrip.test.ts` — **利用者が実際に通る経路** (モデル → ProseMirror → モデル) で
  同じことを見る。あわせて、モデルのマーク属性が往復して戻ることを個別に確かめる

要素数の比較から `w:r` と `w:t` だけ外してある。空セルの
`<w:p><w:r><w:t/></w:r></w:p>` が `<w:p/>` に正規化されるためで、
Word 自身が空セルをそう書く。文字の欠落は本文テキストの比較が捕まえる。

## 未検証の項目

この開発環境には Microsoft Word が無い。

LibreOffice 24.2 は入っているが**壊れている**。`.docx` どころか
プレーンな `.txt` の変換すら `source file could not be loaded` で失敗する
(`soffice --headless --convert-to pdf t.txt`)。Wowd の出力とは無関係の
環境側の問題なので、独立した第 2 実装としては使えない。
再調査の手間を省くためここに記録しておく。

したがって現時点で確認できているのは以下まで:

- zip の整合性 (`unzip -t`)
- 全 XML パートが整形式であること
- 全パートが保存されていること (footnotes / endnotes / comments / fontTable /
  docProps / settings を含む 18 パートすべて)
- 冪等ラウンドトリップ (`read(write(read(f))) === read(f)`)
- エディタ経由の往復 (開く → ProseMirror → 保存 → 開き直す)
- 変更履歴の不変条件 (すべて承諾 = 記録しない場合 / すべて取り消し = 編集前)
- 画面のページ数と PDF のページ数の一致
- WML の子要素順序が順序テーブルどおりであること (`tests/unit/order.test.ts`)
- ECMA-376 の公式 XSD に当てて規格違反が無いこと (`tests/unit/schemaValidation.test.ts`)
- パッケージ全体の参照グラフが閉じていること (`tests/unit/packageIntegrity.test.ts`)
- 壊れた / 悪意のある .docx で落ちないこと (`tests/unit/hostileInput.test.ts`)

### 実機 Word での確認 (2026-09-19 実施・合格)

Windows 版 Microsoft Word で、`npm run word-check` が出す 20 ファイルを確認した。
**すべて修復ダイアログを出さずに開き、確認項目もすべて期待どおりだった。**

当初確かめたかった 3 点は、いずれも合格:

1. Word が「問題を修復しますか」を出さずに開けること
2. 変更履歴の赤入りが Word の校閲画面に正しく出ること
   (段落記号の `w:ins` / `w:del` を含む)
3. コメントのスレッドと解決状態が Word 側でも保たれること
   (`w14:paraId` による結び付け)

ただし**一度目は `11-コメント.docx` が修復ダイアログを出した。**
原因は 2 件で、どちらもこの環境の自動検査を素通りしていた:

- 複数段落にまたがるコメントの範囲を段落ごとに開いて閉じていた
  (同じ `w:id` の範囲と参照が段落数ぶん出る)
- 返信のコメントが本文から参照されていなかった (錨が無い)

**ECMA-376 の XSD はどちらも通す。**
`w:commentRangeStart` / `End` / `w:commentReference` の出現回数に制約が無いため。
加えてフィクスチャ側も同じ誤りを持っていたので、往復テストにも映らなかった。
`src/core/docx/validate.ts` に錨の数と孤立の検査を足し、
`tests/unit/comments.test.ts` に回帰テストを置いた。

**教訓: 規格検証を通ることと Word が開けることは別物。**
実機の確認は代替できない。

### 逆方向 (Word → Wowd) の確認 (2026-09-19 実施)

Word 16 (Office 365) が書いた実物の `.docx` を
`tests/fixtures/docx/real-word16.docx` として読み込み、全テストをかけた。
**利用者の実文書なので `.gitignore` により追跡しない。**
CI では走らないので、受け取った側の環境でのみ効く検査になる。

内容: 見出し / 箇条書きの解除 / コメントと返信 / 変更履歴 (`w:ins`) /
ヘッダーとフッター / 文字サイズ。表と画像は含まれていない。

**こちらで生成したフィクスチャでは 1 件も出なかった欠落が 4 件出た。**
すべて修正済み。

| 何が | どう壊れていたか |
|---|---|
| `w:numPr` に `w:numId w:val="0"` | numId=0 を「リストでない」と解釈して**要素ごと捨てて**いた。これは「この段落だけ箇条書きを外す」という明示の指定なので、捨てるとスタイル側の箇条書きが復活して記号が戻る |
| `w:commentReference` を載せたランの `w:rPr` | 参照は書き出しで作り直すので、Word が付けていた「コメント参照」の文字スタイル・大きさが失われていた |
| `w:p` の属性 (`w14:textId` / `w:rsid*`) | **子要素は raw 退避していたのに属性は落としていた。** Word の文書比較が使う情報が消える |
| `w:sectPr` の属性 (`w:rsid*`) | 同上 |

3 つめを捕まえるため、忠実性テストを**属性まで**広げた
(`lostAttrs`。タグ名込みで (タグ, 属性) 単位に数える)。
広げた直後に、`rawAttrs` を ProseMirror のスキーマに宣言し忘れている
別の欠落が出た。**属性の欠落を見る仕組みが無かったことが、
そもそもの見落としの原因**だった。

あわせて、こちらが**勝手に足していた**属性を 1 件直した。
Word が書いた `<w:cols w:space="425"/>` に `w:num="1"` を補って返していた。
既定値で埋めると、開いて保存しただけで原本と違う属性が増える。

#### 残る差分 (許容する)

実物ファイルの往復で残るのは次の 2 つだけ。

| 差分 | 許容する理由 |
|---|---|
| `w:r` の `w:rsidRPr` | ランはエディタで結合・分割されるので、ラン単位の編集セッション印は原理的に対応を保てない |
| `w:ins` の `w16du:dateUtc` | `w:date` の UTC 表記の控え。Word が書き直す |

`tests/unit/roundTripFidelity.test.ts` と
`tests/unit/editorRoundTrip.test.ts` の `ACCEPTED_ATTR_LOSS` に、
**タグ名込みで**限定して挙げてある
(`w:p` や `w:sectPr` の `w:rsid*` は保持対象なので入れていない)。

#### まだ確認できていないもの

受け取った実文書に**表と画像が入っていない**。
この 2 つについては、こちらで生成したフィクスチャでしか確かめられていない。

### スキーマ検証について

`npm run schema:fetch` で ECMA-376 5th edition **Part 4** の
`OfficeOpenXML-XMLSchema-Transitional.zip` を取得する。
Wowd が書くのは Transitional (`.../wordprocessingml/2006/main`) で、
Part 1 に入っているのは Strict (`purl.oclc.org` 系) なので使えない。

検証の前に MCE (Markup Compatibility) の前処理をする。
`mc:Ignorable` に挙がった接頭辞の要素と属性を落としてから当てる。
`w14:paraId` のような Microsoft 拡張は ECMA-376 の XSD が知らないので、
落とさずに当てると**正しいファイルが不合格になる**。

契約は「違反ゼロ」ではなく **「保存して違反が増えないこと」**。
Wowd は未対応の要素を原文のまま書き戻すので、元が規格外なら出力も規格外になる。
それは忠実さであって不具合ではない。罰すると
「規格に合わせるために中身を捨てる」方向に歪む。

### 順序違反という壊れ方について

ECMA-376 の `CT_PPr` / `CT_SectPr` / `CT_Settings` などは xsd:sequence なので、
子要素の順序は「推奨」ではなく必須。**順序違反は往復テストでは検出できない。**
読み直したモデルは順序が違っても同じになるため。

実際に `SECTPR_ORDER` から `w:headerReference` が漏れており、ヘッダーを持つ
全文書が規定違反の順序で書き出されていた。`emitOrdered` は現在、
順序テーブルに無いタグをモデルが出そうとしたら例外を投げる
(原文のまま退避した断片だけは従来どおり末尾に流す)。

## ページ分割が載せられないもの

ページ分割は「本文を 1 本の縦の流れとして並べ、改ページ位置に空白を挿し込む」
作りになっている。実測 (offsetTop の差分) で位置を決めるので、
日本語の行送りや margin の相殺まで正確に反映でき、計算量も線形に収まる。

その代わり、次の 3 つは**原理的に載らない**。

| | 載らない理由 |
|---|---|
| 段組み | 段を横に並べる必要がある。1 本の縦の流れに空白を挿す方式では表せない |
| 表のページ跨ぎ分割 | 表の行と行のあいだに空白を挿す必要があるが、`<table>` の中に空白要素は置けない (ブラウザが外へ出す) |
| 脚注のページ下部配置 | そのページに載る脚注の量で本文の高さが変わる。本文量 → 脚注量 → 本文高さ という循環になり、一方向の計算では解けない |

直すには「ページごとの箱に内容を流し込む」作りへ変えることになる。
それはページ分割の作り直しであって、ページ数の一致・原稿用紙のマス目・
PDF との一致・性能・カーソル位置の保持という、
**いま動いていて厚くテストされているもの**を全部作り直すことになる。

v1 ではこの作り直しを行わず、**描けないことを画面で伝える**方針を取った
(README の「描けない指定の伝え方」)。読み込み・保存では情報は失われない。
