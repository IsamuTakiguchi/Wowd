# Wowd

Microsoft Word ライクな日本語文書エディタ (Electron デスクトップアプリ)。

実在の `.docx` を開いて編集し、保存しても**元の文書を壊さない**ことを最優先に作っている。

## いまできること

| | 状態 |
|---|---|
| `.docx` を開く / 保存する | ✅ |
| 文字書式 (太字・斜体・下線・取り消し線・サイズ・色・蛍光ペン・上付き下付き・和欧混植フォント) | ✅ |
| 段落書式 (配置・行間・インデント・見出しスタイル) | ✅ |
| 箇条書き / 段落番号 (日本語書式を含む複数レベル) | ✅ |
| 元に戻す / やり直し | ✅ |
| 検索と置換 (正規表現・全角半角・ひらがなカタカナの正規化) | ✅ |
| 用紙サイズと向きの変更 | ✅ |
| styles.xml のスタイル定義を画面に反映 | ✅ |
| 印刷レイアウト (ページ表示) と PDF 出力 | ✅ |
| ヘッダー / フッター・ページ番号 | ✅ 表示・往復・編集 (平文 + 差し込みトークン) |
| ルビ (ふりがな) | ✅ 表示・挿入・編集 |
| 文字数と行数 (原稿用紙) | ✅ 設定ダイアログ・行送り反映・マス目表示 |
| 表 | ✅ 表示・往復 (結合セル含む)・挿入・行列の追加削除・結合分割 |
| 画像 | ✅ 表示・往復・ファイルからの挿入 |
| 目次 | ✅ 見出しからの生成・更新 (Word 側で再計算できる形式) |
| 変更履歴 | ✅ 記録・承諾/元に戻す・変更箇所の移動・著者ごとの色分け・表示モード |
| コメント | ✅ スレッド表示・返信・解決・削除・往復 |
| 自動保存とクラッシュ復帰 | ✅ 30 秒ごとに退避し、次回起動で復元を持ちかける |

**未実装の機能を含む文書も安全に扱える。** 該当部分は編集こそできないが、
保存時に元の内容がそのまま書き戻される。

v1 で予定した機能はすべて実装済み。
描けない指定がいくつか残るが、いずれも読み込み・保存で情報は失われず、
**画面で何が起きているかを伝える**ようにしてある (後述)。

ヘッダー / フッターは「平文 + 差し込みトークン (`{ページ番号}` など)」として編集する。
実際のヘッダーはほぼ 1〜2 行の文字列とページ番号なので、この形で足りる。

**表や画像を含むものは、平文に潰さず段落ごとに直す。**
社名入りのレターヘッドのように、表や画像は触らず文字だけ直したいことが多い。
段落を「道筋 (path)」で指して中身だけ差し替えるので、
触らなかったものは元のまま残り、構造も画像も失われない
(`editableLines` / `applyEditableLines`)。

画像や未対応の要素を含む段落は直せないが、**一覧には出す**。
出さないと、直せない段落があること自体が伝わらず
「なぜか一部だけ直せない」に見えるため。

### 変更履歴について

記録中の編集は、打たれたあとで「挿入には `w:ins`、削除には `w:del`」の形に
書き換えられる。**削除された文字は本当には消さない**。承諾するまでは
文書の一部として残り、取り消せば元に戻る。段落記号そのものの挿入・削除
(Enter と BackSpace) も `w:pPr/w:rPr` の `w:ins` / `w:del` として記録する。
ここを落とすと段落の分割と結合だけが履歴に残らなくなる。

差分の計算は `prosemirror-changeset` に任せている。自前の差分では
貼り付けや一括置換のような大きな編集で破綻するため。

不変条件を単体テストで押さえてある (`tests/unit/trackChanges.test.ts`)。
打鍵・BackSpace・範囲削除・置換・貼り付け・段落の分割と結合のそれぞれで:

- すべて承諾した本文 = 記録しなかった場合の本文
- すべて取り消した本文 = 編集前の本文

### 書式の変更履歴

書式だけを変えた履歴 (`w:rPrChange` / `w:pPrChange`) も記録する。

挿入と削除は `prosemirror-changeset` が差分から見つけてくれるが、
**書式の変更は見つけてくれない** (文字が同じなので差分に出ない)。
そこで、書式を変えるコマンドの**手前**で変更前の書式を控える。
「手前」なのが要点で、変えたあとでは変更前が分からない。

変更前の書式はモデルに持たず、`rawRPr` / `rawPPr` に原文として入れる。
書き出しの順序表が正しい位置へ置くので、規格どおりの並びになる。

同じ箇所の書式を二度変えても、**最初の「変更前」を保つ**。
`w:rPrChange` が指すのは「記録を始める前の姿」であって
「1 つ前の姿」ではない。上書きすると取り消しても元へ戻らなくなる。

承諾・取り消しは挿入・削除と同じ不変条件に従う
(承諾した姿 = 記録しなかった場合 / 取り消した姿 = 編集前)。

表示モード (すべての変更 / 変更なし / 初版) は CSS だけの切り替えで、
**保存される内容は表示モードに左右されない。**

### キーボード操作

Word に合わせてある。

| | |
|---|---|
| Ctrl+N / Ctrl+O / Ctrl+S / Ctrl+Shift+S | 新規 / 開く / 上書き保存 / 名前を付けて保存 |
| Ctrl+P | PDF として保存 |
| Ctrl+Z / Ctrl+Y | 元に戻す / やり直し |
| Ctrl+A | すべて選択 |
| Ctrl+F | 検索と置換 |
| Ctrl+B / Ctrl+I / Ctrl+U | 太字 / 斜体 / 下線 |
| Ctrl+L / Ctrl+E / Ctrl+R / Ctrl+J | 左揃え / 中央揃え / 右揃え / 両端揃え |
| Ctrl+M / Ctrl+Shift+M | インデントを増やす / 減らす |
| Ctrl+Enter | 改ページ |
| Tab / Shift+Tab (リスト上) | レベルを下げる / 上げる |
| Ctrl+Shift+E | 変更履歴の記録を開始 / 終了 |
| Ctrl+Alt+N / Ctrl+Alt+P | 次の変更 / 前の変更 |
| Ctrl+Alt+M | コメントの表示 |
| Ctrl+マイナス / Ctrl+プラス / Ctrl+0 | 縮小 / 拡大 / 100% |

Ctrl+A はネイティブメニューの役割 (`role: 'selectAll'`) ではなく本文のコマンドに
回している。役割の方はブラウザ既定の全選択で、選択状態が ProseMirror へ
非同期にしか伝わらず、「選択されているか」で決まる操作が一拍遅れて反応するため。

### 日本語組版の制約

「文字数と行数」は、**純粋な日本語の文章では指定した文字数どおりに折り返す**
(CJK の字は 1em 幅なので割り切れる)。ただし英数字が混ざる行はグリッドから
ずれて、次の段落で揃い直す。Word の `snapToChars`
(半角文字がマス目を整数個消費し、次の CJK 字がマス目に吸着し直す) は
CSS のテキストレイアウトでは再現できない。

原稿用紙の用途 (小説・学術論文の投稿規定) は純日本語なので、そこでは正確に出る。

### 画像の回り込み

`w:drawing` の回り込み指定を CSS に写す。画面と PDF で同じ関数を使う
(`src/core/css/imageCss.ts`)。別々に書くと見た目が食い違うため。

| OOXML | 写し方 |
|---|---|
| `wrapSquare` / `wrapTight` / `wrapThrough` | `float`。左右は `wp:positionH` の指定で決める |
| `wrapTopAndBottom` | 行を占める `block` |
| `wrapNone` (前面 / 背面) | **写さない。**行の流れに残す |

前面 / 背面は座標で本文の裏表に置くもので、位置の基準と座標を
CSS の `absolute` にそのまま写すと**かえってずれる**。
ずれてはいても、どこに何があるかは分かる状態にしておく。

外周に沿う回り込み (`wrapTight`) の多角形は CSS では表せないので、
四角と同じ扱いにする。

### 描けない指定の伝え方

**黙って落とさない**のがこの製品の方針だが、落とさないだけでは足りない。
読み込めていて保存でも戻るのに画面に出ない指定は、利用者から見れば
「Wowd で開いたら消えた」になる。**何が起きているかまで伝える。**

| 何を | いつ | どう伝えるか |
|---|---|---|
| 段組み | 読み込み時 | 「段組み (1 段で表示します)」 |
| 脚注・文末脚注 | 読み込み時 | 「脚注の配置 (本文の流れの中に置きます)」 |
| 表のページ跨ぎ | **はみ出したときだけ** | 「ページに収まらない表があります」 |

表は読み込み時には判断できない。1 ページに収まるかは組んでみないと
分からないので、実際に紙からはみ出したときにだけ知らせる。
収まる表では何も出さない。

未対応要素の名前は `src/core/docx/unsupportedLabels.ts` で日本語に直す。
生のタグ名 (`w:footnoteReference`) を並べても何が起きたか伝わらない。
**表に無いものはタグ名のまま出す。**黙って隠すより、見慣れない名前でも
出ているほうがよい。名前が分からないのはこちらの手落ちであって、
利用者に知らせない理由にはならない。

### v1 で意図的に落としている範囲

ページ分割は次を扱わない。いずれも「保持はするが、レイアウトはしない」:

- 表のページ跨ぎ分割 (ページに収まらない表は次ページへ丸ごと送る)
- 脚注・文末脚注のページ下部への配置
- 画像の回り込み (`wrap` は inline として描く)
- 段組みの描画 (`w:cols` は往復するが 1 段で描く)

ページ数が Microsoft Word と完全に一致することも約束しない。行分割の実装が
違うため、長い文書では 1〜2 ページずれうる。**約束しているのは
「画面のページ表示と Wowd 自身の PDF 出力が一致すること」**で、
これは E2E で毎回検証している。

## 設計上の要点

読む前に知っておくと全体が理解しやすい判断が 4 つある。

### 1. パッケージ保存型ラウンドトリップ

`.docx` を開いたら**全パートをバイト列のまま保持し続け**、保存時は
実際に変更したパートだけを差し替える。

生成型のライブラリは自分のモデルからパッケージを組み立て直すので、
知らないパート (`theme1.xml`、rsid 付きの `settings.xml`、`customXml/`、
`fontTable.xml` など) を全部落としてしまう。顧客のファイルを開いて保存したら
壊れる、は製品として成り立たない。

本文の中でも、モデル化していない要素は `rawBlock` / `rawRun` /
`rawPPr` / `rawRPr` に原文のまま退避して書き戻す。
**preserve by default, model by exception.**

### 2. リストは入れ子ノードではなく段落属性

Word にリストのコンテナは存在しない。リストとは `w:numPr`
(`numId` + `ilvl`) を持つ**兄弟段落の並び**で、見た目は全部
`numbering.xml` にある。

`bulletList > listItem > paragraph` で持つと、実際の Word 文書に頻出する
非単調な `ilvl` の並びが import → export で壊れる。
そのため行頭記号は文書本体に入れず、ProseMirror の Decoration として重ねている。

### 3. 単位は OOXML ネイティブのまま

twip (1/20pt)、half-point、EMU のまま保持し、CSS px への変換は
描画の直前だけで行う。途中で px に落とすと丸め誤差がそのまま
ラウンドトリップの差分になる。

### 4. 拡大縮小は transform、zoom は使わない

Chromium の CSS `zoom` はレイアウトに影響する。フォントサイズを実際に変えて
行分割をやり直すので、**倍率を変えるだけで改ページ位置が動く**。
それでは画面と PDF が一致しない。`transform: scale()` なら見た目だけが
変わるので、実測値も改ページ位置も倍率に依存しない。

### 5. 印刷は画面ではなく専用の HTML から

画面をそのまま印刷するのではなく、ページ分割の結果から
「1 ページ 1 div」の静的な HTML を組んで出力する。
同じ改ページ位置を使うので、画面と PDF の一致が
結果的にではなく構造的に保証される。

印刷用文書は独自スキームの専用セッションで開く。本文をディスクに書かずに済み、
メインウィンドウより厳しい CSP (`script-src 'none'`) をヘッダで付けられる。

### 6. 解析はレンダラ側のワーカー

main プロセスではなくレンダラの Web Worker で動かす。
main が固まるとメニューバーもウィンドウ操作も全部固まるが、
ワーカーなら何も固まらない。最高権限の main に XML パーサを置かないのは
単純に衛生的でもある。

## 検証について

`.docx` の忠実性は次の自動テストで担保している。

1. 書き出したパッケージのパート一覧が元の上位集合であること
2. 書き換えていないパートがバイト一致すること
3. `read(write(read(f))) === read(f)` (冪等ラウンドトリップ)
4. **ECMA-376 の公式 XSD に当てて規格違反が無いこと**
5. **パッケージ全体の参照グラフが閉じていること**
   (`r:id` の解決・Content_Types の被覆・コメント範囲の対応)
6. **要素と文字が 1 つも減らないこと** (`tests/unit/roundTripFidelity.test.ts`)

6 が要るのは、**3 の冪等性だけでは情報の欠落を捕まえられない**ため。
読み取りが落とし、書き出しも出さない要素は 2 回目もやはり落ちるので、
モデルは一致して素通りする。実際に `w:pPrChange` がこの穴を通っていた。

加えて、**実際の利用経路 (開く → エディタ → 保存 → 開き直す) でも**検証している
(`tests/unit/schemaCoverage.test.ts`、`tests/unit/editorRoundTrip.test.ts`、
`tests/e2e/editorRoundtrip.spec.ts`)。

モデル層のテストだけではこの経路を通らないため、次の種類のバグを検出できない。
どちらも実際に起きた:

- ProseMirror のスキーマに無いノード / マークが読み込み時に例外になり、
  エディタに前の文書が残ったまま保存されて中身がすり替わる
  (表・画像・ルビ・フィールド・変更履歴・コメントで発生)
- prosemirror-tables が「列数が合わない」と判断して勝手にセルを足し、
  開いて保存しただけで表の構造が変わる
- **ProseMirror がスキーマに宣言の無いマーク属性を黙って捨てる。**
  モデルとスキーマで属性の形が違うと、開いて保存しただけで書式が消える
  (フォント・文字サイズ・下線の種類と色で発生)。
  Word は修復ダイアログを出さないので、実機で開いても気づけない

### 往復テストでは原理的に検出できない壊れ方

**順序違反と名前空間の欠落は、往復テストを必ず素通りする。**
読み直したモデルは、順序が違っても宣言が足りなくても同じに見えるため。
しかし Word はどちらも開けない。

実際に次を作り込んでいて、どれも往復テストは緑のままだった:

- `sectPr` の子要素順に `w:headerReference` が無く、末尾へ回っていた
- `w:tblBorders` の辺をオブジェクトのキー順のまま出していた
- `w:drawing` が `wp:` を宣言していなかった
- `numbering.xml` を書き直すと `w15:` の宣言だけが消えていた
- 複合フィールド (`w:fldChar`) を `<w:r>` で包み直さず、`w:p` の直下に出していた

前の 4 つは ECMA-376 の XSD 検証で、最後は同じ検証の「保存して違反が増えていないか」で
見つかった。順序テーブルへの追加漏れは `emitOrdered` が例外を投げて止める。

後者は OOXML と ProseMirror で表のモデルが違うことによる。OOXML は縦結合の
継続セルを各行に明示するが、ProseMirror は開始セルの rowspan だけで表す。
`src/renderer/editor/serialize/tableGrid.ts` で明示的に変換している。

**実機 Windows 版 Microsoft Word で確認済み (2026-09-19)。**
`npm run word-check` が出す 20 ファイルすべてが、修復ダイアログを出さずに開き、
変更履歴・コメントのスレッドと解決状態・ヘッダー / フッター・目次が
Word 側で期待どおりに扱われることを確認した。

その確認で、自動検査をすり抜けた不具合が 2 件出た。どちらも修正済み:

- 複数段落にまたがるコメントの範囲を**段落ごとに開いて閉じて**いた。
  同じ `w:id` の範囲と参照が段落数ぶん出て、Word が修復を出す
- 返信のコメントが本文から参照されていなかった (錨の無いコメント)

どちらも ECMA-376 の XSD は通る (出現回数に制約が無いため)。
**規格検証だけでは Word 互換を保証できない**ことの実例として記録しておく。
同種の欠陥は `src/core/docx/validate.ts` の錨の検査で捕まえるようにした。

**逆方向 (Word で作った `.docx` を Wowd が壊さず開けるか) も確認済み。**
Word 16 が書いた実物を `tests/fixtures/docx/real-*.docx` に置けば、
上記のテストが自動的に拾う (利用者の実文書なので追跡はしない)。

そこで、こちらで生成したフィクスチャでは 1 件も出なかった欠落が 4 件出た:

- `w:numPr` の `w:numId w:val="0"` (「この段落だけ箇条書きを外す」の明示) を捨てていた
- `w:commentReference` を載せたランの書式を捨てていた
- **`w:p` と `w:sectPr` の属性** (`w14:textId` / `w:rsid*`) を捨てていた
  — 子要素は raw 退避していたのに、属性を見る仕組みが無かった

いずれも修正済み。忠実性テストを属性まで広げてある。
許容している差分と、まだ確認できていないもの (表・画像を含む実文書) は
`docs/round-trip-report.md` にある。

実機確認の手順とチェックリストは **`docs/word-verification.md`** にある。
確認用ファイルは `npm run word-check` で生成でき、
生成のあと「確認対象が実際に入っているか」まで自動で検査する
(画面操作は静かに失敗しうるので、空振りしたファイルを渡さないため)。

## 配布

```bash
npm run icon       # アイコンを作り直す (原本は resources/icon.svg)
npm run package    # いまの環境向けにパッケージする
```

配るときは**タグを打つだけ**でよい。
`.github/workflows/release.yml` が Windows・macOS・Linux の
それぞれでビルドし、GitHub のリリースに載せる。

```bash
git tag v0.1.0 && git push origin v0.1.0
```

Linux の AppImage と deb は生成と起動まで確認済み。
Windows の `.exe` と macOS の `.dmg` は、それぞれその環境でしか作れない。

**電子署名は未実施。**無くても動くが、Windows は SmartScreen が警告し、
macOS は Gatekeeper が起動を止める。証明書の取得は本人確認が要るので
利用者本人の手続きになる。

手順とつまずきどころは **`docs/release.md`** にまとめてある。
